# DeployCheck: Agent Instructions

## Project goal

DeployCheck is a small, practical pre-deployment checker for developers. It scans a project for common configuration and secret-handling mistakes, then returns actionable findings with evidence and remediation guidance.

**Core pitch:** Catch deployment mistakes before they become production problems.

Build a dependable MVP first. Do not turn this into a large platform or claim that a scan guarantees an application is secure.

## Stack and conventions

- **Language:** Python
- **Backend:** FastAPI
- **Validation and schemas:** Pydantic
- **Tests:** pytest
- **HTTP/API tests:** FastAPI TestClient or HTTPX, whichever is already configured
- **Lint/format:** Follow the existing repository configuration. Do not introduce a new toolchain unless needed.
- **Persistence:** Avoid a database for the initial MVP unless a demonstrated requirement makes it necessary.
- **Interface:** Keep the API usable by a simple frontend or API client. Do not build an elaborate frontend before the scanner works.

Use type hints, small functions, clear names, and straightforward modules. Prefer the standard library where it is sufficient.

## MVP scope

Prioritize these capabilities:

1. **Project file discovery**
   - Scan an explicitly supplied local project directory or a safely handled uploaded archive, depending on the current interface.
   - Skip virtual environments, dependency folders, build outputs, VCS metadata, caches, and other clearly irrelevant directories.
   - Use an allowlist of text/configuration file types where practical.
   - Apply file-count, file-size, and total-size limits.

2. **Secret-pattern checks**
   - Detect likely credentials using documented patterns, such as private-key headers, common token formats, and suspicious assignments to names like `API_KEY`, `SECRET`, `TOKEN`, or `PASSWORD`.
   - Treat matches as potential findings, not definitive proof.
   - Never return the full secret in API responses, logs, exceptions, or reports. Redact matched values.
   - Include file path and line number when available.
   - Avoid scanning binary files.

3. **Environment variable checks**
   - Detect variable references in supported files and compare them with declarations in `.env.example` or other explicitly supported configuration sources.
   - Report likely missing declarations and empty required values where this can be established.
   - Do not require users to provide a real `.env` file.
   - Never expose values from `.env` files in findings.

4. **Configuration checks**
   - Add a small set of explainable checks, such as a missing `.gitignore`, a potentially tracked `.env` file, or a suspicious debug setting.
   - Make each rule's assumptions and limitations clear.
   - Do not label a project unsafe solely because a recommended file is absent.

5. **Findings and report**
   - Return structured findings with a stable rule ID, title, severity, summary, evidence, file path, line number if available, and recommended fix.
   - Support JSON output. Add Markdown export if time permits.
   - If displaying a readiness score, document how it is calculated. Do not imply it is a formal security certification.

## API design

Keep the API small and versionable. A reasonable initial shape is:

- `GET /health` — basic service health.
- `POST /api/v1/scans` — scan a safely provided project or uploaded archive, depending on the chosen ingestion design.
- `GET /api/v1/scans/{scan_id}` — only if scan results are persisted; persistence is optional for the MVP.

Use Pydantic models for request/response schemas. Return useful HTTP status codes and safe error messages. Never include stack traces, secrets, absolute server paths, or raw uploaded content in client-facing errors.

If accepting ZIP uploads:
- Reject path traversal entries and absolute paths.
- Never extract files outside a dedicated temporary directory.
- Limit compressed and uncompressed sizes, file count, nesting where practical, and scan duration.
- Reject or skip symlinks and unexpected file types.
- Clean up temporary files on success and failure.
- Do not execute, import, or run any scanned project code.

Prefer local directory scanning for the first working prototype if upload handling would delay delivery.

## Security and privacy requirements

- **Do not execute scanned code.** Static inspection only.
- **Do not send source code, environment files, or secrets to external AI services.**
- **Do not print or store raw secrets.** Redact values in findings and logs.
- Do not commit real credentials, personal data, or private project files.
- Do not scan arbitrary server paths supplied by an unauthenticated client. Restrict scanning to a controlled workspace or use safe uploads.
- Prevent path traversal and symlink escapes.
- Treat filenames and file contents as untrusted input.
- Keep error responses generic while preserving useful diagnostic details in server-side development logs.
- Explain that checks can produce false positives and false negatives.

## Finding schema

A finding should contain fields similar to:

```json
{
  "rule_id": "SECRET001",
  "title": "Possible hardcoded credential",
  "severity": "high",
  "message": "A value resembling a credential was detected.",
  "file_path": "config/settings.py",
  "line_number": 12,
  "evidence": "API_KEY = [REDACTED]",
  "recommendation": "Move the credential into an environment variable and rotate it if it was exposed."
}
```

Use a severity enum such as `critical`, `high`, `medium`, `low`, and `info`. Define severity deliberately and consistently.

## Testing requirements

Write tests for the rules and API. At minimum, cover:

- A clean project with no findings.
- A project containing a fake hardcoded secret.
- Secret redaction in API responses and logs.
- A missing environment-variable declaration.
- A benign string that should not trigger a secret rule, where relevant.
- Ignored directories and binary files.
- Invalid paths and unreadable files.
- ZIP path traversal and size limits if ZIP upload is supported.
- Stable response schemas and safe error responses.

Use fake credentials in all tests. Tests must not depend on real secrets, external APIs, or network availability.

## Development workflow

1. Inspect the existing repository before editing.
2. Identify the current entry point, dependencies, and tests.
3. Implement one small vertical slice at a time.
4. Add or update tests with every rule.
5. Run the relevant tests after changes, then run the full suite.
6. Keep dependencies minimal and update `requirements.txt` when necessary.
7. Update the README with setup, run, test, scope, and limitations.
8. Never claim tests passed unless they were actually run.

Typical commands, adapted to the repository's environment:

```bash
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# macOS/Linux:
# source .venv/bin/activate

pip install -r requirements.txt
uvicorn app.main:app --reload
pytest -q
```

## Out of scope for the first release

Do not build these unless all core MVP features work and time remains:

- User accounts, billing, teams, or a hosted project-history dashboard.
- A custom AI model or mandatory LLM integration.
- Automatic code changes or automatic deployments.
- A claim that the app certifies a project as secure.
- Broad language-specific static analysis across every framework.
- Complex cloud scanning, integrations, or background-job infrastructure.

## Definition of done

The MVP is ready to demonstrate when:

- A developer can run it from the README instructions.
- The scanner identifies known issues in the unsafe sample project.
- The safe sample project produces no unexpected high-severity findings.
- Each finding explains the problem and suggests a concrete next step.
- Secret values are redacted everywhere user-visible.
- The API handles invalid input safely.
- Tests cover the core rules and pass.
- The repository contains no real credentials.
- The demo shows a scan, the findings, fixes, and a rescan.

When in doubt, prefer a smaller, tested, honest feature over a larger, unreliable one.
